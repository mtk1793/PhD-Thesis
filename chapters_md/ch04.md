## 4.2 Development of the Brain-Inspired AI Framework

### 4.2.1 System 1: CNN-LSTM Reflexive Controller

The System 1 network maps a window of 12 encoded observations onto the nine continuous setpoints of Table 4.2. Its architecture, shown in Figure 4.1, is implemented exactly as follows: a one-dimensional convolution Conv1d(1 to 64, kernel 3, same padding) followed by ReLU; a second convolution Conv1d(64 to 64, kernel 3, same padding) followed by ReLU; an adaptive average pooling to one value per timestep; an LSTM with input size 64 and hidden size 128 operating along the time axis; an additive attention head formed by a Linear(128 to 128) layer, a Tanh activation, and a Linear(128 to 1) layer with softmax normalisation over time; and a classification head of Linear(128 to 64), ReLU, Dropout(0.1), and Linear(64 to 9). The convolutions operate independently on each timestep of the window, extracting a 64-dimensional spatial signature per observation, and the LSTM then integrates those signatures across time with a hidden state that persists between control steps and is reset only on episode boundaries, following the recurrent formulation of [32] and the attention formulation of [34].

![Figure 4.1: CNN-LSTM architecture of the System 1 reflexive controller.](figures/fig_cnnlstm_arch.png)

The LSTM replaces the plain recurrent unit precisely because its gated memory can carry information across the 12-hour window without vanishing gradients [32]. At timestep $t$, with input $x_t$ and previous hidden and cell states $h_{t-1}$ and $c_{t-1}$, the forget gate is

```eq
%%4.1
f_t = \sigma(W_f\, [h_{t-1},\, x_t] + b_f)
```

and the input and output gates follow the same affine-then-sigmoid pattern,

```eq
%%4.2
i_t = \sigma(W_i\, [h_{t-1},\, x_t] + b_i)
```

```eq
%%4.3
o_t = \sigma(W_o\, [h_{t-1},\, x_t] + b_o)
```

where each $W$ concatenates the recurrent and input weight matrices and each bias is additive. The cell state then blends old memory with candidate memory,

```eq
%%4.4
c_t = f_t \odot c_{t-1} + i_t \odot \tanh(W_c\, [h_{t-1},\, x_t] + b_c)
```

and the hidden state exposes the filtered memory,

```eq
%%4.5
h_t = o_t \odot \tanh(c_t)
```

with $\odot$ denoting the elementwise product. The three gates let the network discard stale observations, admit new ones, and reveal only the relevant part of the memory, which is exactly the behaviour a reflexive power system controller needs when a disturbance at one hour must still influence setpoints several hours later.

The attention head replaces the common practice of using only the last hidden state with a learned, weighted summary of all twelve timesteps. For hidden state $h_j$ at window position $j$, the head computes the score

```eq
%%4.6
e_j = v^T \tanh(W_a\, h_j + b_a)
```

normalises the scores into attention weights

```eq
%%4.7
a_j = \frac{\exp(e_j)}{\sum_{m=1}^{T} \exp(e_m)}
```

and forms the context vector

```eq
%%4.8
c^{\mathrm{ctx}} = \sum_{j=1}^{T} a_j\, h_j
```

which the fully connected head maps through the 64-unit ReLU layer and the dropout of [100] onto the nine outputs. Algorithm 4.1 states the complete inference path as it runs in the deployed controller, including the sliding-window maintenance and the final projection into the action box, which is the step that connects this algorithm to Proposition 3.1.

**Algorithm 4.1: System 1 inference (CNN-LSTM reflexive controller).**

```text
Input: observation obs at step t; window buffer W (max length 12);
       persistent hidden state (h, c); model parameters theta_1
Output: control setpoints u^(1) mapped to FACTS and EV dispatch

 1: x_raw <- StateEncoder.encode(obs)              // 160 features (Table 4.3)
 2: W.append(x_raw)                                // sliding window update
 3: if length(W) > 12: drop oldest entry
 4: while length(W) < 12: prepend copy of x_raw    // warm-start padding
 5: X <- stack(W) shaped (1, 12, 160)
 6: Z1 <- ReLU(Conv1d_k3(X))                       // 1 -> 64 channels, per timestep
 7: Z2 <- ReLU(Conv1d_k3(Z1))                      // 64 -> 64 channels
 8: P  <- AdaptiveAvgPool1d(Z2)                    // (1, 12, 64)
 9: (h, c) <- LSTM(P, (h, c))                      // Equations (4.1) to (4.5)
10: e_j <- v^T tanh(W_a h_j + b_a) for j = 1..12   // Equation (4.6)
11: a <- softmax(e);  ctx <- sum_j a_j h_j         // Equations (4.7), (4.8)
12: u_raw <- W2 ReLU(W1 ctx + b1) + b2             // 128 -> 64 -> 9
13: u^(1) <- clip(u_raw, lo, hi)                   // project into action box A
14: map u^(1) to {SVC_14, STATCOM_39, TCSC_16_17, UPFC_26, EV_3, EV_8, EV_15}
15: return controls
```

The deployed feasibility of Algorithm 4.1 depends on the size of the parameter vector, both for memory allocation on the real-time core and for the honesty of the latency claims, so the count is derived exactly rather than quoted approximately.

**Proposition 4.1 (Exact parameter count of the System 1 network).**
*Statement.* The trainable parameter count of the architecture of Figure 4.1 is exactly 137,418, that is, approximately 0.14 million parameters.

*Proof.* Each layer contributes weights plus biases, summed over the six trainable blocks. First, Conv1d(1 to 64, kernel 3) contributes 1 × 64 × 3 weights and 64 biases, giving 192 + 64 = 256. Second, Conv1d(64 to 64, kernel 3) contributes 64 × 64 × 3 weights and 64 biases, giving 12,288 + 64 = 12,352. Third, the LSTM with input size 64 and hidden size 128 contributes four gate blocks, each with input weights 128 × 64, recurrent weights 128 × 128, and two biases of length 128, giving 4 × (8,192 + 16,384 + 128 + 128) = 4 × 24,832 = 99,328. Fourth, the attention head contributes Linear(128 to 128) with 16,384 + 128 = 16,512 parameters and Linear(128 to 1) with 128 + 1 = 129 parameters, giving 16,641. Fifth, the first fully connected layer contributes 128 × 64 + 64 = 8,256. Sixth, the output layer contributes 64 × 9 + 9 = 585. The total is 256 + 12,352 + 99,328 + 16,641 + 8,256 + 585 = 137,418, which completes the proof.

The 137,418 figure should be compared with the approximately 250K parameter figure quoted in the Phase 4 project report: the larger number counts parameter storage together with the optimiser state and serialisation buffer overhead rather than the trainable network alone, and the exact trainable count is the value derived above. The distinction matters for the hardware budget of Section 4.7, because the deployed inference graph carries only the 137,418 trained values, roughly 0.55 MB in single precision, while the training-time optimiser state never leaves the offline workstation. An analytical operation count reinforces the point: one forward pass costs on the order of 1.4 million multiply-accumulate operations, dominated by the LSTM term of 12 × 4 × 128 × (64 + 128), a workload that dedicated embedded hardware executes well inside the 5 ms budget once the Python overhead identified in Section 4.7 is removed.

### 4.2.2 System 2: QIRL Deliberative Controller

The deliberative controller implements the quantum-inspired reinforcement learning scheme of Section 3.5 in executable form. It maintains a register of 32 candidate action vectors, one per dimension of Table 4.2 per candidate, and holds the decision state as the amplitude vector of the quantum state

```eq
%%4.9
|\psi\rangle = \frac{1}{\sqrt{Z}} \sum_{a \in \mathcal{A}_c} \sqrt{\exp(\beta Q(s, a))}\; |s, a\rangle, \qquad Z = \sum_{a \in \mathcal{A}_c} \exp(\beta Q(s, a))
```

in direct correspondence with the quantum computation formalism of [58] and the quantum reinforcement learning lineage of [59], [60], [61]. The amplitudes start uniform at $1/\sqrt{32}$ and the candidates start as uniform samples of the action box, so the initial policy is maximum entropy within the feasible set. The action-value function $Q$ is instantiated by the immediate candidate reward

```eq
%%4.10
r_i = -\frac{1}{n_{\mathrm{bus}}} \sum_{k=1}^{n_{\mathrm{bus}}} |V_{m,k} - 1| - 0.05\, n_{\mathrm{viol}} - 0.001\, \Vert a_i \Vert_2^2
```

which scores every candidate against the current network state in a single vectorised pass, and the amplitude reinforcement update is

```eq
%%4.11
\alpha_i(t+1) = \frac{\exp(\beta r_i / 2)}{\sqrt{\sum_{j} \exp(\beta r_j)}}
```

with inverse temperature $\beta = 5.0$. Selection applies the Born rule $P(a_i) = |\alpha_i|^2$ by sampling the register, and the implementation applies the max-shift to the rewards before the exponentials are taken, which Section 3.5 showed leaves every probability ratio unchanged; the update deserves a formal treatment because it carries both the learning dynamics and the numerical safety of the controller.

**Theorem 4.1 (Exact norm preservation and shift invariance of the amplitude update).**
*Statement.* For any reward vector $r = (r_1, \dots, r_{32})$ and $\beta > 0$, the amplitude update of Equation (4.11) produces an amplitude vector with $\Vert \alpha \Vert_2 = 1$ exactly. Moreover, the induced selection distribution is invariant to any common reward shift $r_i \mapsto r_i + c$, $c \in \mathbb{R}$, and the implemented max-shift $c = -r_{\mathrm{max}}$ is a special case that only prevents floating-point overflow.

*Proof.* Squaring the component of Equation (4.11) gives $|\alpha_i|^2 = \exp(\beta r_i) / \sum_{m} \exp(\beta r_m)$, since the numerator squares to $\exp(\beta r_i)$ and the denominator squares to the sum in the radical. Summing over $i$ yields $\sum_i |\alpha_i|^2 = \sum_i \exp(\beta r_i) / \sum_m \exp(\beta r_m) = 1$, so the norm is exactly one. For the shift invariance, substitute $r_i + c$: the numerator becomes $\exp(\beta(r_i + c)/2) = \exp(\beta c/2)\exp(\beta r_i/2)$ and the denominator becomes $\exp(\beta c/2)\sqrt{\sum_j \exp(\beta r_j)}$, and the common factor $\exp(\beta c/2)$ cancels in the ratio, so every amplitude, and hence every selection probability, is unchanged. Choosing $c = -r_{\mathrm{max}}$ rescales the largest exponent argument to zero, which keeps all exponentials in the interval $(0, 1]$ and thereby inside floating-point range; the additional $10^{-12}$ guard in the implemented normalisation is a numerical safety margin only. This completes the proof.

Algorithm 4.2 assembles the full evaluation cycle of the controller as it runs each step, from candidate scoring through amplitude update and Born-rule selection to tunnelling.

**Algorithm 4.2: QIRL candidate evaluation and selection.**

```text
Input: network state (bus voltages vm); candidate register C (32 x 9);
       amplitudes alpha (32); beta = 5.0; tunnel rate 0.1
Output: deliberative action u^(2); updated amplitudes and candidates

 1: for i = 1 to 32:                               // vectorised in implementation
 2:     dev    <- mean_k |vm_k - 1|
 3:     n_viol <- #{k : vm_k < 0.95 or vm_k > 1.05}
 4:     r_i    <- -dev - 0.05 n_viol - 0.001 ||C_i||_2^2   // Equation (4.10)
 5: r <- r - max(r)                                // common shift c = -r_max
 6: alpha_i <- exp(beta r_i / 2);  alpha <- alpha / ||alpha||_2   // Equation (4.11)
 7: P_i <- |alpha_i|^2;  i* <- sample index from P // Born-rule selection
 8: u^(2) <- C_{i*}
 9: M <- max(1, int(0.1 * 32)) = 3                 // tunnelling quota
10: re-sample M candidates uniformly in the action box A
11: return u^(2)
```

Two properties of Algorithm 4.2 deserve emphasis because they distinguish it from value-based deep reinforcement learning [22], [23]. First, the controller requires no offline training whatsoever: the reward evaluation of lines 1 to 4 queries the current power flow state directly, so the controller is operational the moment it is instantiated on any system for which an action box can be defined, which the comparison results in Chapter 11 confirm on the January 2019 benchmark. Second, the tunnelling quota of lines 9 and 10 guarantees that three candidates, roughly 10 percent of the register, are re-randomised every step regardless of how concentrated the amplitudes have become, so the policy can never fully cease exploring; this is the mechanism that let the deliberative controller escape the local preferences of its initial register in the benchmark runs. The framework specification sets the design target of 58 to 59 percent faster convergence than deep Q-network baselines for this mechanism, a design figure examined further in Section 11.4, and the planning horizon of 6 steps remains reserved for future multi-step rollouts as noted in Section 3.5.

### 4.2.3 The Metacognitive Arbiter

The arbiter implements the arbitration law of Section 3.2 in executable form. It computes the stress metric $c_1 = \mathrm{mean} |V_m - 1.0|$ from the current voltage magnitudes and evaluates

```eq
%%4.12
\alpha(c_1) = \sigma(\tau_{\mathrm{arb}}\,(c_{\mathrm{th}} - c_1)), \qquad c_{\mathrm{th}} = 0.03,\; \tau_{\mathrm{arb}} = 50
```

and then blends every FACTS scalar and every EV setpoint according to

```eq
%%4.13
u = \alpha(c_1)\, u^{(1)} + (1 - \alpha(c_1))\, u^{(2)}
```

The blending is applied componentwise over the nine-dimensional action box, so the arbiter never needs to reason about individual devices; it only decides how much authority each pathway receives. Three properties of the arbitration weight make it suitable for closed-loop control and are recorded formally below.

**Proposition 4.2 (Smoothness and monotonicity of the arbitration weight).**
*Statement.* The arbitration weight $\alpha(c_1)$ of Equation (4.12) is smooth ($C^{\infty}$) in $c_1$, strictly monotonically non-increasing in $c_1$, satisfies $\mathrm{d}\alpha/\mathrm{d}c_1 = -\tau_{\mathrm{arb}}\, \alpha(1 - \alpha)$, and obeys the bound $|\mathrm{d}\alpha/\mathrm{d}c_1| \leq \tau_{\mathrm{arb}}/4 = 12.5$ for all $c_1$.

*Proof.* The sigmoid $\sigma$ is real-analytic with derivative $\sigma'(z) = \sigma(z)(1 - \sigma(z))$, and $\alpha(c_1)$ is the composition of $\sigma$ with the affine map $z = \tau_{\mathrm{arb}}(c_{\mathrm{th}} - c_1)$, so $\alpha$ is $C^{\infty}$ as a composition of smooth functions. The chain rule gives $\mathrm{d}\alpha/\mathrm{d}c_1 = \sigma'(z) \cdot (-\tau_{\mathrm{arb}}) = -\tau_{\mathrm{arb}}\, \alpha(1 - \alpha)$. Since $0 < \alpha < 1$ for every finite $c_1$, the factor $\alpha(1-\alpha)$ is positive, so the derivative is negative and the weight is strictly monotonically non-increasing in stress. The quadratic $g(\alpha) = \alpha(1-\alpha)$ attains its maximum of $1/4$ at $\alpha = 1/2$ on $(0, 1)$, hence $|\mathrm{d}\alpha/\mathrm{d}c_1| \leq \tau_{\mathrm{arb}}/4 = 50/4 = 12.5$. This completes the proof.

The bounded slope of 12.5 per unit stress means the authority transfer is fast exactly where it matters, around the threshold, yet never instantaneous, which avoids the chattering that a hard switching law between two controllers would exhibit near the decision boundary. The blend output remains feasible without further projection because of the convexity established in Proposition 3.1, which we restate here as applied to the arbiter.

**Proposition 4.3 (Feasibility of the blended command).**
*Statement.* If $u^{(1)} \in \mathcal{A}$ and $u^{(2)} \in \mathcal{A}$, then the blended command of Equation (4.13) satisfies $u \in \mathcal{A}$ for every attainable value of $\alpha(c_1) \in (0, 1)$.

*Proof.* By Proposition 3.1 the action box $\mathcal{A}$ is convex and closed under convex combinations with any weight in $[0, 1]$. Equation (4.13) is such a convex combination with weight $\alpha(c_1)$, and Proposition 4.2 shows $\alpha(c_1) \in (0, 1)$ for every finite stress value, so $u \in \mathcal{A}$ follows directly from Proposition 3.1 without repeating its argument. This completes the proof.

**Algorithm 4.3: Metacognitive Arbiter blending cycle.**

```text
Input: observation obs; System 1 action u^(1); System 2 action u^(2);
       threshold c_th = 0.03 p.u.; sharpness tau_arb = 50
Output: blended command u; arbitration mode

 1: vm <- obs.bus voltage magnitudes
 2: c1 <- mean |vm - 1.0|                          // stress metric
 3: alpha <- sigmoid(tau_arb * (c_th - c1))        // Equation (4.12)
 4: for each FACTS scalar and EV setpoint index j: // Equation (4.13)
 5:     u_j <- alpha * u1_j + (1 - alpha) * u2_j
 6: mode <- classify(c1, alpha, health flags)      // Table 4.4
 7: append alpha to arbitration history
 8: return u, mode
```

Algorithm 4.3 classifies each cycle into one of five design modes, and Table 4.4 states the mode conditions and the associated action. The Stage-1 implementation executes the blended core of lines 1 to 5 at every step and reserves the full mode machine, including the override and safe-mode entries, for the deployment build, but the classification logic is already present in the arbitration history and in the health monitoring of Section 4.5. In the January 2019 benchmark the mean stress of 0.0286 p.u. sits just below the 0.03 p.u. threshold, so $\alpha = \sigma(50 \times 0.0014) \approx 0.52$ on average and the blend is genuinely mixed; the resulting controller tracks the deliberative pathway, 2813 violation bus-hours against 2810 for System 2 alone, while retaining the reflex capability that the deliberative pathway alone cannot provide, as reported in Section 11.1.

**Table 4.4: Metacognitive Arbiter decision modes and thresholds.**

| Mode | Condition | Action |
|---|---|---|
| SYSTEM_1_REFLEX | Stress well below threshold, alpha near 1 | System 1 executes alone; System 2 idle |
| BLENDED | Stress near threshold, alpha between the mode margins | Convex blend of Equation (4.13) |
| SYSTEM_2_PLANNING | Stress above threshold, alpha near 0 | System 2 setpoints dominate |
| SYSTEM_2_OVERRIDE | Sustained stress over consecutive cycles, or System 1 output invalid | Force u = u^(2) regardless of alpha |
| SAFE_MODE | Non-convergent power flow, telemetry loss, or actuation bound violation | Revert to validated safe setpoints; re-initialise recurrent states |

Conceptually, the arbiter plays the role that affective neuroscience assigns to metacognitive monitoring, and the design borrows its vocabulary from the artificial emotion literature: the fast pathway behaves as an artificial amygdala in the sense of Picard [19] and Minsky [20], reacting to threat signatures before deliberate appraisal completes, while the arbiter supplies the appraisal that decides whether the reflexive reaction should stand. No separate amygdala module is implemented; the analogy is functional, not structural, and it motivates the threshold-and-slope form of Equation (4.12) rather than any learned switching policy. The same reasoning explains why the enhanced TD3 actor-critic of the wider literature, which addresses function approximation error with twin critics and delayed policy updates over the continuous-control foundations of [24], is treated in this thesis as a classical continuous-control baseline rather than as a component of the reflex path: TD3 learns its own action distribution offline and offers no native mechanism for the fast-slow authority split, whereas the CNN-LSTM plus QIRL pairing provides it structurally, and the comparative discussion is taken up again in Chapter 5.

## 4.3 Multi-Layer Control Hierarchy Implementation

The hierarchy of Section 3.3 becomes executable through three concrete mechanisms, one per tier. At the *device tier*, each shunt FACTS device runs a local droop characteristic that provides voltage support even when the supervisory layer is unreachable, which preserves the defence-in-depth property expected of primary control. For device $j$ with local voltage measurement $v_{m,j}$ and reference $V_{\mathrm{ref}}$, the commanded susceptance is

```eq
%%4.14
b_j = \min\{\max(K_p\,(V_{\mathrm{ref}} - v_{m,j}),\; B_{\min}),\; B_{\max}\}
```

with the clamp inherited from the device model of Equation (3.8), so the local loop can never exceed the rating regardless of the droop gain; the gain itself is tuned in Chapter 5, where the small-signal condition that keeps the loop stable is derived. The EV stations run their local SoC supervision with the dispatch rule proved invariant in Proposition 3.2, which plays the same role at the fleet stations that the droop clamp plays at the shunt devices.

At the *regional tier*, neighbouring devices and fleets must agree on shared quantities such as corridor flows and zone voltages, and CAPSM implements this agreement with the alternating direction method of multipliers in the standard scaled form of Boyd and colleagues [44]. Each region $i$ holds a local copy $x_i$ of its setpoints, a consensus variable $z$ carries the agreed inter-regional quantities, and a scaled dual $u_i$ accumulates the disagreement. The three updates per iteration are

```eq
%%4.15
x_i^{k+1} = \mathrm{argmin}_{x_i}\; \left(f_i(x_i) + \frac{\rho}{2}\, \Vert x_i - z^k + u_i^k \Vert_2^2\right)
```

```eq
%%4.16
z^{k+1} = \mathrm{argmin}_{z}\; \left(g(z) + \frac{N \rho}{2}\, \Vert z - \bar{x}^{k+1} - \bar{u}^k \Vert_2^2\right)
```

```eq
%%4.17
u_i^{k+1} = u_i^k + x_i^{k+1} - z^{k+1}
```

where $f_i$ is the regional objective, $g$ the consensus penalty, $N$ the number of regions, $\rho$ the penalty parameter, and the bars denote averages across regions; the z-update of Equation (4.16) reduces to an average when $g$ is the standard quadratic. Algorithm 4.4 states the loop in the form deployed for the two-zone partition of the IEEE 39-bus system.

**Algorithm 4.4: Regional coordination by ADMM consensus.**

```text
Input: regional objectives f_1, f_2; consensus variable z; scaled duals u_1, u_2;
       penalty rho; tolerance epsilon
Output: coordinated regional setpoints x_1, x_2

 1: initialise z from the last system-tier dispatch; u_1 <- 0; u_2 <- 0
 2: repeat
 3:     for each region i:                            // x-update, Equation (4.15)
 4:         x_i <- argmin_x ( f_i(x) + (rho/2) ||x - z + u_i||^2 )
 5:     x_bar <- (x_1 + x_2) / 2;  u_bar <- (u_1 + u_2) / 2
 6:     z <- x_bar + u_bar                            // z-update, Equation (4.16)
 7:     for each region i:                            // u-update, Equation (4.17)
 8:         u_i <- u_i + x_i - z
 9:     s_pri <- ||x_i - z||;  s_dual <- rho ||z^{k+1} - z^k||
10: until s_pri < epsilon and s_dual < epsilon
11: broadcast z as the agreed inter-regional dispatch
```

At the *system tier*, the dual-process core of Section 4.2 supplies the global dispatch that initialises the consensus variables, so the hierarchy is not three independent loops but one loop with three reaction speeds. The system tier also owns the objectives that no regional loop can see, such as the total loss term in the reward weights of Section 3.7, and it arbitrates between regional requests when the consensus loop converges to a compromise that the stress metric judges unacceptable. This arrangement follows the convergence doctrine for ADMM in [44], with the formal convergence statement and its residual-decay sketch deferred to Chapter 9 where the multi-area optimisation is analysed in full.

## 4.4 Data Flow Architecture

Every claim in this chapter ultimately rests on the data path that carries measurements into the controllers and commands back out, so the path is specified as an algorithm rather than left to implementation folklore. Algorithm 4.5 states the acquisition-to-actuation pipeline that executes once per control cycle.

**Algorithm 4.5: Telemetry-to-actuation pipeline.**

```text
Input: PMU streams (IEEE C37.118), SCADA and IEC 61850 telemetry,
       meter and weather feeds
Output: actuation commands to FACTS, EV, and DER interfaces

1: acquire telemetry frames from all sources
2: align frames to the IEEE 1588 (PTP) grandmaster clock   // common time base
3: estimate the system state (WLS estimator or EMS-provided state)
4: encode the estimated state with the StateEncoder        // 160 features
5: run System 1 inference (budget 5 ms) and System 2 evaluation (budget 50 ms)
6: blend with the Metacognitive Arbiter                    // Algorithm 4.3
7: apply the safety filter: clamp to the action box, EV SoC guards,
   validity checks against the estimator residuals
8: dispatch commands to device interfaces; stamp and log for feedback
```

The state estimate of line 3 is produced, when the framework operates autonomously, by the weighted least squares estimator that minimises the measurement residual

```eq
%%4.18
\hat{x} = \mathrm{argmin}_{x}\; \sum_{i=1}^{m} w_i\, (z_i - h_i(x))^2
```

where $z$ collects the measurements, $h$ the measurement functions, and $w_i$ the inverse-variance weights, following the classical formulation of [74]. The estimator serves two purposes in the pipeline: it supplies the noise-cleaned state that the encoder consumes, and its residuals feed the chi-squared screening test that protects the control loop against false data injection, a defence analysed in full in Chapter 7. When the framework runs in advisory mode inside an existing EMS, line 3 simply consumes the utility estimator output instead, which is the integration path described in Section 3.8.

The safety filter of line 7 is deliberately the last stage before actuation and deliberately independent of learning. It re-clamps every command to the action box of Proposition 3.1, re-checks the EV commands against the SoC guards of Proposition 3.2, and rejects any command that would move a measurement residual outside the screening threshold, so that even a fully misbehaving learning layer can only slow the framework down, never push a device past its rating. The feedback side of the pipeline closes the loop: every stamped command and the subsequent network response are logged, and the logs feed the performance monitor of Section 4.5 and the evaluation reports of Chapter 11.

## 4.5 Real-Time Adaptation Mechanisms

Deployment is not a frozen state, and the framework adapts along four mechanisms with different timescales. The first mechanism is online parameter adaptation of the System 1 network. After behaviour cloning, the network continues to learn from the arriving trajectory with gradient updates

```eq
%%4.19
\theta_{t+1} = \theta_t + \eta_t\, \nabla_{\theta} L(\theta_t)
```

where $L$ is the squared-error objective against the demonstrated or improved targets and $\eta_t$ is the learning rate, implemented with the Adam optimiser of [99] in the offline stage. Adaptation is gated: updates are applied only when the recent reward trend and the residual screen both indicate that the incoming data are trustworthy, so a contaminated stream, for example during a telemetry fault, pauses learning instead of poisoning it. The same gating philosophy governs any future reward-based fine-tuning, which remains flagged as future work in the Stage-1 build.

The second mechanism is the hidden-state reset policy of the recurrent controller. The LSTM state of Section 4.2.1 persists across control steps by design, which lets the network integrate the 12-hour window, but persistence becomes a liability when the statistical regime changes abruptly. The controller therefore resets its hidden state and its window buffer to the warm-start configuration on three triggers: an episode boundary in evaluation, a confirmed topology change such as the line 16–17 trip of the contingency scenario, and a declared safe-mode entry by the arbiter. The third mechanism is the amplitude re-initialisation of System 2: whenever the arbiter switches into SAFE_MODE or a contingency is confirmed, the amplitude vector returns to the uniform state $1/\sqrt{32}$ and the candidate register is re-sampled uniformly in the action box, which restores maximum-entropy exploration exactly when the old amplitudes, tuned to the pre-event state, would be most misleading. Both mechanisms together ensure that neither pathway carries stale memory across a regime change.

The fourth mechanism is performance monitoring, which turns the logs of Algorithm 4.5 into deployment oversight. A rolling window tracks the violation count, the mean stress $c_1$, the arbitration weight history, the inference times of both pathways, and the convergence flag of the power flow, and each track carries an expected envelope from the offline validation. Sustained drift outside an envelope triggers graduated responses: recency-weighted retraining of the cloned network, adjustment of the QIRL inverse temperature, and, in the limit, demotion of the framework to advisory mode. The monitoring design deliberately reuses the same metrics that Chapter 11 reports, so the operator interface, the acceptance tests, and the published evaluation all speak one measurement language, and the 52-test verification suite of Appendix B anchors the unit-level behaviour of every mechanism listed here.

## 4.6 Validation Framework and Methodology

The validation methodology proceeds in layers that mirror the V-model adopted in Chapter 10: unit tests verify each component against its specification, subsystem tests verify the interfaces, full-system tests verify the closed loop on the benchmark, and the HIL campaign verifies the timing claims on hardware. The unit layer is anchored by the 52-test pytest suite accumulated across the six build phases, all passing, and the full-system layer is the January 2019 benchmark defined in Section 11.1; this section documents the two learning-specific layers between them, the training of System 1 and the online validation of System 2.

System 1 is trained by behaviour cloning from a rule-based demonstrator, the supervised pretraining strategy whose no-regret properties are analysed in the imitation learning literature [22], [33]. The demonstrator is the RuleBasedVoltage controller; the demonstration set consists of 4 episodes drawn from January 1, 8, 15, and 22 of 2019, one week apart to sample the weekly load pattern, with 168 hourly steps per episode for 672 training samples in total. Training minimises the mean squared error between the network output and the demonstrator action with the Adam optimiser [99] at learning rate 1e-3, gradient clipping at 1.0, and 100 epochs, completing in 116.7 s on a CPU. The empirical risk declines monotonically across the run: the loss is 0.002026 at epoch 10, 0.001556 at epoch 50, 0.000990 at epoch 80, and 0.000759 at epoch 100. Because behaviour cloning is empirical risk minimisation over a fixed demonstration set, and the loss surface of the network is smooth in the parameters, the observed monotone decline is consistent with convergence of the Adam iterates toward a stationary point of the empirical risk in the sense of [33]; no claim of global optimality is made, and the deployment consequences of this limitation are examined through the evaluation below rather than assumed away.

System 2 requires no training, so its validation is necessarily online: the controller is instantiated with the hyperparameters of Section 4.2.2 and evaluated directly on the benchmark scenarios, and its validation evidence consists of the convergence record, the violation counts, and the inference timings reported in Chapter 11. The blended CAPSM controller is validated in the same runs, which exercises the arbiter, both pathways, and the safety filter simultaneously and leaves no component validated only in isolation. Table 4.5 lists the five scenario families that constitute the full-system validation, together with the metrics each scenario contributes; the scenarios are chosen so that every requirement of Table 4.1 is exercised by at least one of them.

**Table 4.5: Key test scenarios for validation.**

| Scenario | Description | Metrics |
|---|---|---|
| Normal operation | January 2019 QSTS, 721 h of real OPSD load, wind, and solar on IEEE 39 | Violation bus-hours, mean voltage deviation, losses, convergence, ms per step |
| N-1 line trip | Line 16–17 out at 2019-01-15 12:00, with restoration | Losses 51.1 to 58.7 MW (+14.9 percent), minimum voltage 0.9505 p.u., 13 of 13 steps converged, restoration to pre-event state |
| Ramp events | Largest national ramps applied: 1-h +20,040 / −20,128 MW, 3-h +28,390 / −23,588 MW | Ramp-following behaviour, voltage excursions, FACTS and EV response |
| FDI attack | False data injection into the telemetry consumed by the controllers [71], [72] | Residual statistic response, detection behaviour, false alarm rate |
| EV V2G response | Bidirectional steps of up to 50 MW at buses 3, 8, 15 with SoC bounds [0.2, 0.9] and eta 0.92 | SoC trajectory within bounds, voltage support, energy accounting |

The scenario set deliberately spans the two failure families that the safety analysis cares about, physical stress and information stress. The first two scenarios and the ramp family stress the physics, and they are the scenarios on which the 2847-bus-hour baseline and the controller improvements of Chapter 11 are measured. The FDI family stresses the information layer, and it is the scenario family that connects this chapter to the detection architecture of Section 3.6 and the attack analysis of Chapter 7. The EV family, finally, validates the actuation guarantees proved in Proposition 3.2 by driving the fleets to their bounds and verifying that the trajectory never leaves the permitted envelope.

## 4.7 Computational Implementation for Real-Time Deployment

The offline implementation is written in Python with PyTorch [35] and NumPy [120], and its measured execution times expose exactly why the real-time port is necessary. The System 1 pathway measured 63.0 ms per step in the Phase 4 standalone evaluation and 32.0 ms per step in the Phase 6 integrated build, the latter reflecting profiling-driven tightening of the encoder and the inference wrapper; both figures sit far above the 5 ms budget of Equation (3.19). The decomposition of the overhead is unambiguous: the network itself costs on the order of 1.4 million multiply-accumulate operations per forward pass, as derived in Section 4.2.1, which mainstream embedded hardware executes in well under a millisecond, so the measured time is dominated by the Python interpreter, the framework dispatch layers, and the per-call memory traffic around the model rather than by the mathematics. System 2 measured 21.1 ms per step standalone in Phase 5 and 27.6 ms in the integrated build, inside its 50 ms budget even before porting, because the candidate evaluation is a vectorised arithmetic loop with no neural network involved; the blended CAPSM loop measured 36.5 ms per step in the integrated build.

The porting path follows two stages with a common intermediate representation. In the first stage, the trained System 1 graph is exported to the Open Neural Network Exchange format [101], which decouples the trained weights from the training framework and lets the real-time target execute the graph in a compiled runtime; the export is verified by comparing outputs of the exported graph and the original model to machine precision across the validation set. In the second stage, the exported graph is compiled for the deployment targets of the four-core allocation: the System 1 task as a compiled real-time task on Core 1, with an FPGA realisation through the eFPGASIM toolchain as the sub-millisecond option where the timing margin demands it, and the System 2 task as a multi-threaded real-time task on Core 2, since its arithmetic maps naturally onto vector units without any neural network machinery. The arbiter and the safety filter are fixed-point-friendly arithmetic blocks of a few hundred floating-point operations, which execute trivially inside their 10 ms and 1 ms periods on Cores 3 and 4.

Table 4.6 states the code-to-hardware traceability that carries every component of this chapter to a named deployment target with a measured offline time and a target time, so that the gap analysis of the port is a table lookup rather than an investigation.

**Table 4.6: Code-to-hardware traceability for real-time deployment.**

| Component | Offline implementation | HIL deployment target | Measured (ms per step) | Target |
|---|---|---|---|---|
| System 1 CNN-LSTM | PyTorch model in Python loop | Core 1 compiled task, ONNX runtime, eFPGASIM option | 63.0 (Phase 4), 32.0 (Phase 6) | Below 5 |
| System 2 QIRL | Vectorised NumPy controller | Core 2 multi-threaded real-time task | 21.1 (Phase 5), 27.6 (Phase 6) | Below 50 |
| Metacognitive Arbiter | Sigmoid blend in Python | Core 3 coordination task | Within 36.5 blended loop | Below 10 |
| Safety filter | NumPy clamping and SoC guards | Embedded in Core 1 to 3 tasks | Included in loop time | Below 1 |
| I/O interface | Python environment bindings | Core 4 I/O task with protocol gateways | 1 ms period task | Below 1 |
| Logging | pandas and CSV writers | Core 4 logging task, asynchronous | Non-blocking | Below 1 |

The traceability table closes the design loop opened by Section 3.9: every component has a core, a budget, and a measured starting point, and the hardware campaign of Chapter 10 verifies the endpoint. Two engineering conclusions follow from the table. First, the only component whose port carries schedule risk is System 1, and the risk is bounded because the FPGA option provides an order-of-magnitude margin over the budget; the measured 32 ms is a property of the offline host, not of the algorithm. Second, the blended loop time of 36.5 ms already satisfies the deliberative budget of Equation (3.19) even on the offline host, which means the dual-process architecture degrades gracefully: if the reflex path were unavailable, the framework would still meet its supervisory obligations through System 2 alone, a resilience property that the arbitration design of Section 4.2.3 makes explicit and that the HIL campaign tests directly.

## 4.8 Conclusion

This chapter turned the CAPSM architecture of Chapter 3 into an executable design. The requirement table tied every component to a control gap, the action and observation interfaces were fixed at nine outputs and 160 inputs respectively, and the dual-process core was specified exactly: the CNN-LSTM reflex with its gated dynamics and attention head, the QIRL deliberator with its amplitude dynamics and tunnelling exploration, and the sigmoid arbiter that blends them. The formal results secure the design: Proposition 4.1 fixed the trainable footprint at exactly 137,418 parameters, Theorem 4.1 proved that the amplitude update preserves the unit norm exactly and is invariant to reward offsets, Proposition 4.2 bounded the arbitration slope at 12.5 per unit stress and established its monotonicity, and Proposition 4.3 carried the blending feasibility of Chapter 3 into the executable arbiter. The hierarchy implementation, the data pipeline, and the adaptation mechanisms specified how the design behaves outside the laboratory, and the validation methodology defined the scenarios against which the design must answer.

Three properties of the implemented framework stand out for the chapters that follow. First, feasibility is structural rather than statistical: the action box, the device clamps, the SoC invariant, and the safety filter guarantee that no learned command can leave the designed envelope, which is what allows an AI controller to be connected to a transmission network at all. Second, the deliberative pathway requires no training data, which makes the framework deployable on new systems without a data collection campaign and which the results of Chapter 11 confirm empirically. Third, every component already has a named hardware destination and a measured starting time, so the remaining distance to real-time deployment is engineering rather than research. Chapter 5 now addresses the design decisions that this chapter deliberately left open, the placement of the FACTS devices and the tuning of the controller parameters, and Chapter 10 completes the deployment story with the four-core HIL campaign on the OPAL-RT platform.
